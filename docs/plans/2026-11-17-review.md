# /decide:review: agreed plan

Source: the owner's swipe round `1-2f5b16` on 2026-11-17, 38 cards, none skipped. One answer went against the recommendation: everything ships in one release instead of a narrow first cut.

## What we get

A third skill in the plugin. The owner says "review what you did", the agent calls `review`, and a page opens on the branch's diff against its base. The page has three layers.

1. **Overview** (first screen). What changed and why, a list of risks that jump to the risky chapter, and a map of the parts and how they call each other. The agent describes the links; code that did not change but depends on what did is drawn dashed, with its call sites. Checks are listed as command, exit code and duration, as the agent ran them. The page runs nothing. Red or missing checks do not block the review; they are shown as they are, and "Approve" warns.
2. **Chapters** instead of files. The agent groups hunks from different files by meaning, in the order of the idea, tests next to the code they cover, a risk mark on each chapter. Mechanical edits (renames, formatting, lock files) fold into one line with a count. Every hunk lands in a chapter; what the agent left out goes to "The rest", and "sorted N of M" stays visible. A switch puts the same hunks in file order, and the file tree opens on a button.
3. **Diff.** Syntax highlighting, expand to the whole file, "where is this used" by name, and a question to the agent under any hunk (the existing `explain`). A change to the UI is shown with the before/after slider the page already has (`ui/js/media/compare.js`).

Comments go on a line, as text, with a kind: fix, question, nit. A chapter is marked read as a whole. Findings of a separate reviewer agent come only when the owner asks; they arrive on the open page next to their lines, can be hidden, and each one is accepted or dismissed. A comment can be marked "make it a rule": the agent adds a line to the repo's `AGENTS.md` together with the fixes.

The review ends with one of three verdicts: approve, approve with nits, return. The agent answers questions at once and edits code only after the verdict. Merging stays with the agent under the repo's own rules. The second round shows what changed since the first and the status of every comment; the full diff is one switch away. On a phone: overview, a one-column diff and the verdict.

## The agent's loop

1. Run the checks, write the spec (why, chapters, mechanical groups, map, affected code, checks), call `review {project, spec, base?, head?}`. The server takes the snapshot and answers with the round id, the URL and lint warnings such as "7 hunks in no chapter".
2. `wait` returns a question on a hunk (answer with `explain`), a request for reviewer findings (run a fresh reviewer, send its findings with `patch`), or the verdict with all comments.
3. After "return": fix, then call `review` again with `previous: <round>`. The agent states for each comment what it did: fixed, answered, or declined and why.

## How to build

- **Git, read only.** New `lib/git.mjs`: `execFile("git", …)` with fixed argument lists and no shell, cwd at the project top, subcommands limited to `rev-parse`, `merge-base`, `diff`, `show`, `ls-files`, `grep`. Refs and paths from the spec are checked before use: nothing that starts with `-`, no path outside the snapshot's file list.
- **Snapshot.** At open the server resolves base and head to commits and saves the diff in the round's folder, so the review survives a restart and a later commit. When the tree moves on, the page shows "newer exists" and nothing else changes.
- **Round.** `mode: "review"` beside `questions` and `swipe` in `lib/store/rounds.mjs`; comments, read marks, finding decisions and the verdict are events in the same log. The spec schema lives in `lib/registry`, so the tool schema, `lint` and the docs come from one place.
- **Page.** `ui/js/review/` and `ui/css/review.css` in the same tab and server. `ui/js/diff.js` already pairs lines; it gets a parser for git's unified diff and loads chapters as they scroll into view. The highlighter is vendored and pinned in `ui/vendor`, like mermaid, and loaded on demand.
- **Names.** The dialog that lists answers before sending is called "review" in the README, the key hints and the `review.*` strings. It becomes "check", so "review" means one thing.
- **Skill.** `skills/review/SKILL.md`: how to cut chapters, what counts as mechanical, how to describe links and affected code, how to report comment statuses.

Order, because one release was chosen over a narrow first cut: (0) a mockup of the overview and one chapter, agreed through `/decide`; (1) git, snapshot, chapters, diff, comments, verdict; (2) the owner reviews the review branch itself with it; (3) second round, map, affected code, findings, rules, phone; (4) rename, docs, release. A flaw in the chapter idea should show at step 2, before step 3 is built on it.

## How we check

- Unit: unified-diff parser (renames, binary files, no trailing newline), hunk-to-chapter assignment and the leftover count, snapshot and "newer exists", the diff between two snapshots, comment anchors that survive it, spec lint, the verdict digest.
- Security: a ref or path that starts with `-`, a path outside the project and a file not in the snapshot are refused, each with a test.
- Playwright on a fixture repository: overview → chapter → one comment of each kind → a question → verdict; a second round with only the changes and comment statuses; findings arriving on an open page and hidden by the switch; phone width.
- By hand: step 2 above, in light and dark theme. We look at the screenshots ourselves.

## What we don't do

- GitHub or GitLab: opening a PR by number, posting comments to it.
- Line coverage, an editor for suggested lines, a commit-by-commit view, splitting a large change into several rounds.
- A page that runs tests or merges. A server that parses imports for the map.
- A reviewer agent that starts on its own before every review.
- A merge to `master` or a release without asking the owner.

## Left to the builder

Which highlighter (measure its size and language list first); whether the map is mermaid built from the agent's nodes and edges or its own SVG; how a chapter names a hunk (file plus line range is the starting point); the version number.

## Risks

- The overview, the map and the "mechanical" label are the author's word, and the independent reviewer runs only on request. The page labels them "as the agent says"; the folded count and the usage search are the cross-check.
- Findings shown next to the code steer the eye, and a chapter marked read does not prove every hunk was read.
- Search by name is noisy for short names.
- `AGENTS.md` grows with every rule; each new line shows up in round two as an ordinary change.
